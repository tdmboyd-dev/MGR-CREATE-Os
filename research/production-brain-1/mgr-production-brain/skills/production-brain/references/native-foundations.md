# Plugin-first native production foundations

These are bounded implementation decisions for MGR Production Brain 1. The plugin executes these functions itself. They do not stand in for research or implementation of the separate rendering, character, VFX and DCC capabilities.

## Durable projects, assets and revisions

1. Definition: persist validated production plans, append-only asset versions and exact asset bytes in a local project database.
2. Production use: resume work, preserve approved prior revisions, recover originals and stop changed files masquerading as unchanged references.
3. Standards: SHA-256 byte identity; SQLite transactions and foreign keys; existing MGR plan/lock contract.
4. Papers: no learned method or new database algorithm is required for this bounded function; database transactions and cryptographic identity are the applicable established methods.
5. Implementations: inspected Creation OS AssetRegistry/digest and reproduced their identity/mutation failures; inspected Node SQLite documentation pinned to the executed v24.21.0 runtime and official SQLite transaction semantics. Compared a process-local Map, separate content-addressed files, and one SQLite database. Choose SQLite for atomic metadata+small-asset storage and restart behavior. Larger media will require a streaming object-store adapter.
6. Models: none. Content hashing does not identify a person or establish asset rights.
7. Datasets: generated byte fixtures; same name/different bytes; stale revisions; missing/cross-project parent IDs; restart; duplicate versions; corruption and concurrent-connection fixtures.
8. Licensing: MGR implementation independently authored. SQLite/Node are runtime components; their distribution terms remain with those runtimes. No third-party database source is copied into the plugin.
9. APIs/providers: local node:sqlite; no provider credential or paid call is needed.
10. Native alternative: MGR ProductionStore with stored prior-revision validation, bound-byte receipts and append-only asset lineage.
11. Runtime: Node 24.21.0 verified to expose DatabaseSync and SQLite 3.53.4. CPU/disk only; no owner GPU requirement. Synchronous operations are bounded for local CLI use.
12. Cost: no API charge; disk storage scales with unique bytes, metadata with revisions. Measure local operation timings; do not describe disk/storage as universally free.
13. Failure modes: stale writers, changed source files, mutable returned objects, duplicate version numbers, missing parents, partial updates, oversized files and database corruption. A local database is not a multi-tenant cloud authorization service.
14. Evaluation: inspect persisted rows and exact recovered bytes after reopening; run negative and competing-connection tests.
15. Placement: standalone plugin projects own their local database. Existing Creation OS projects retain canonical ownership and must use an explicit import/export boundary.
16. Acceptance: a changed byte changes identity; duplicate/stale edits fail without partial state; lock removal cannot evade the stored prior plan; returned data cannot mutate history; exports reproduce stored bytes; incomplete asset inspection never becomes media approval.

## Camera geometry and path checks

1. Definition: check physical camera inputs and a piecewise-linear camera path against declared static axis-aligned collision proxies; project declared subject bounds at supplied camera samples.
2. Production use: catch impossible moves and unintended framing before paying for synthesis or creating DCC animation.
3. Standards: explicit metre world coordinates; millimetre lens/sensor dimensions; right/up/forward camera basis; normalized viewport coordinates; finite times and ordered samples.
4. Papers: this bounded implementation uses established slab intersection and pinhole projection, not a learned camera model. Learned controllers remain a distinct researched candidate path with separate evaluation.
5. Implementations: inspect Three.js Ray.intersectBox, PerspectiveCamera focal/FOV/projection routines and Ray tests; compare with Creation OS's structural-only checks and the earlier USD unit investigation. The Three.js tests cover inside, outside, parallel and coplanar rays. Our finite segment domain and clearance expansion are explicit independent adaptations.
6. Models: none needed for deterministic geometry. Text prompts and CameraCtrl outputs cannot serve as collision evidence.
7. Datasets: analytic boxes/segments, zero motion, tangent contacts, reversed direction, degenerate look-at, negative lens, near-plane intersections and subject-screen bounds.
8. Licensing: Three.js root MIT license inspected; no Three.js source is vendored. MGR implements the established mathematics independently.
9. APIs/providers: native computation; returns a digest-bound report usable before any provider.
10. Native alternative: exact finite-segment/static-AABB intersection and conservative cubic clearance expansion, plus pinhole projection of eight subject-bound corners.
11. Runtime: Node/CPU; cost scales with path-segment × collider count and sample × subject count. Apply explicit input limits.
12. Cost: no API call; benchmark bounded local scenes. AABB proxies trade accuracy for speed and can over-report collisions.
13. Failure modes: wrong units, incomplete proxies, moving objects, curved interpolation, near-plane crossings, collinear up/forward vectors, false precision and treating sampled framing as continuous visibility.
14. Evaluation: known analytic outcomes, invariance under translation, input rejection and digest changes after any geometry edit.
15. Placement: plugin native preflight. Reports state their geometry/interpolation coverage and never certify unseen geometry or a generated video.
16. Acceptance: a collision between keyframes is detected; parallel/tangent/inside cases behave conservatively; invalid physical values fail; near-plane framing is flagged unavailable; sampled framing does not claim continuous visibility.

## Bounded asset inspection

1. Definition: identify exact bytes and inspect supported media structure before reference admission.
2. Production use: distinguish a valid supported input from a misleading filename, truncated file or unsupported format.
3. Standards: PNG Third Edition chunk/header/CRC/compression rules; RIFF/WAVE chunk structure; existing FFprobe research for wider codec coverage.
4. Papers: N/A for this structural inspector; standardized binary formats, not learned reconstruction, define the behavior.
5. Implementations: compare direct bounded structural checks with FFprobe metadata and full decode. The native path handles a declared narrow PNG/PCM-WAVE subset; broader containers remain explicit UNKNOWN until a verified probe/decoder adapter runs.
6. Models: none. Structural inspection is not visual quality, identity, consent or rights verification.
7. Datasets: tiny generated valid fixtures; CRC/length/order corruption; oversized dimensions; decompression ceiling; unsupported bit depth/interlace; odd RIFF chunk padding; inconsistent PCM block alignment.
8. Licensing: MGR parser/checks independently authored; Node zlib/crypto are runtime facilities. No image or audio asset rights are inferred.
9. APIs/providers: local buffers only; no network URLs followed and no automatic uploads.
10. Native alternative: bounded byte inspection returning measured facts, coverage and explicit limitations. Preserve declared MIME separately from detected type.
11. Runtime: CPU; input, pixel and decompressed-output ceilings. Unknown formats may be stored with an uninspected receipt, never accepted as probed media.
12. Cost: one byte hash and bounded parsing/decompression; memory bounded by configured input/output caps.
13. Failure modes: spoofed extension/MIME, chunk overrun, CRC damage, nonconsecutive image data, decompression expansion and unsupported encodings.
14. Evaluation: corrupt each required boundary and confirm rejection; preserve exact byte receipt on supported files; distinguish parse coverage from complete media decode.
15. Placement: shared native module consumed directly by the plugin's asset-store command.
16. Acceptance: unsupported formats are explicit; malformed supported formats fail; facts come from bytes; resource ceilings apply before allocation; metadata cannot substitute for decoded/rendered quality.

## Implemented boundaries

The CLI uses bounded file reads and exclusive output creation. PNG inspection caps input at 32 MiB, pixels at 16 million, expanded scanlines at 64 MiB and chunks at 100,000. Unsupported encodings return an explicit state. Camera evaluation caps sample/box pairs at 100,000. These are MGR engineering limits, not format-standard limits. Media receipts describe structure, not artistic quality. Native SQLite runtime use does not copy or redistribute third-party database source.
